# Document Generation Service — Design

**Date:** 2026-09-21
**Status:** approved for implementation planning

## Intent and first deliverable

Build a separate `document-service` that creates a PDF certificate of
enrolment in the background. A client creates a durable document job, polls
its status, and downloads the produced PDF only after the job completes.

The service establishes the common pipeline for future contracts, receipts,
and acts. The first implementation renders only a certificate; it does not
pretend to implement those other document types.

## Decisions

- Run the service on Python 3.13. Celery 5.6.3 declares support through
  Python 3.13, not Python 3.14.
- Use FastAPI, synchronous SQLAlchemy with `psycopg`, PostgreSQL, Alembic,
  Celery, RabbitMQ, MinIO, Jinja2, and WeasyPrint.
- Keep the HTTP API, dispatcher, Celery worker, and migrations as separate
  Compose services. API and worker reuse the same image.
- Use a dedicated `documents-postgres` container and volume. The document
  service never stores its tables in Schedule Service's database.
- Use MinIO as an S3-compatible object store. Generated PDFs are private;
  the API proxies download through an authenticated-in-the-future endpoint.
  The first slice has no authentication, but it never returns a public MinIO
  URL.
- Store a rendering snapshot in the job's JSONB payload. The certificate API
  receives `student_full_name`, `class_name`, and `academic_year`; this slice
  does not call or construct a student-profile service.
- Create `document_jobs` and `document_task_outbox` in one PostgreSQL
  transaction. A dispatcher publishes the job ID to Celery and later marks
  the outbox row published.
- Celery task delivery is at-least-once. The worker is idempotent: one job ID
  maps to exactly one MinIO object key, `certificates/{job_id}.pdf`.

## Architecture

```text
POST /documents/certificates
  → Document API
  → transaction: document_jobs + document_task_outbox
  → Document dispatcher
  → Celery task through RabbitMQ: generate_certificate(job_id)
  → Celery worker
  → render HTML to PDF, upload to MinIO, update document_jobs

GET /documents/{job_id}
  → status and, when completed, document content endpoint

GET /documents/{job_id}/content
  → API reads the PDF from MinIO and returns application/pdf
```

RabbitMQ is the broker used by Celery to move a background command from the
dispatcher to a worker. `generate_certificate(job_id)` is a task, not a
cross-service business event. The worker receives only the durable job ID;
it reads the rendering snapshot from PostgreSQL itself.

## Data model

### `document_jobs`

| Column | Type | Rule |
|---|---|---|
| `id` | UUID primary key | Generated by the API; public job identifier and stable idempotency key for file storage. |
| `document_type` | `VARCHAR` | First allowed value: `certificate`. |
| `status` | `VARCHAR` | One of `pending`, `processing`, `completed`, `failed`. |
| `payload` | `JSONB` | Immutable rendering snapshot supplied at job creation. |
| `object_key` | nullable `VARCHAR` | `certificates/{id}.pdf` only after a successful upload. |
| `error_message` | nullable `VARCHAR` | Public-safe failure explanation after a terminal rendering failure. |
| `created_at` | `TIMESTAMPTZ` | Database timestamp. |
| `updated_at` | `TIMESTAMPTZ` | Database timestamp on each state change. |

### `document_task_outbox`

| Column | Type | Rule |
|---|---|---|
| `id` | UUID primary key | Durable identity of this delivery intent. |
| `document_job_id` | UUID foreign key, unique | Exactly one initial generation intent per job. |
| `task_name` | `VARCHAR` | `documents.generate_certificate`. |
| `published_at` | nullable `TIMESTAMPTZ` | Null until the dispatcher successfully asks Celery to publish. |
| `created_at` | `TIMESTAMPTZ` | Database timestamp. |

The API transaction commits both rows or neither. A dispatcher crash after
task publication but before `published_at` may publish the same job again;
the worker's stable object key and state checks make that safe.

## HTTP contract

### Create certificate

`POST /documents/certificates`

Request body:

```json
{
  "student_full_name": "Иван Петров",
  "class_name": "7А",
  "academic_year": "2026/2027"
}
```

Success response: `202 Accepted`.

```json
{
  "id": "<uuid>",
  "document_type": "certificate",
  "status": "pending"
}
```

Invalid request fields use FastAPI's normal `422` response. The first slice
does not expose a client-provided idempotency key.

### Read status

`GET /documents/{job_id}` returns `200` for an existing job. It includes
`id`, `document_type`, `status`, `created_at`, and, only for a completed
job, `download_url` equal to `/documents/{job_id}/content`. A missing job
returns `404` with `{"detail": "Document was not found"}`.

### Download content

`GET /documents/{job_id}/content` returns `application/pdf` for a completed
job and streams the object stored at `object_key`. It returns `409` with
`{"detail": "Document is not ready"}` for `pending` or `processing`, `409`
with `{"detail": "Document generation failed"}` for `failed`, and `404` for
an unknown job.

## Job lifecycle and failures

```text
pending
  → processing       worker claims the job
  → completed        PDF has uploaded to MinIO and object_key is saved
  → failed           permanent rendering/input error
```

Temporary infrastructure errors, such as MinIO being unavailable, use
Celery retry with bounded attempts and exponential backoff. When retries are
exhausted, the worker records `failed` with a safe message. Rendering errors
that cannot become valid through retry transition directly to `failed`.

The worker never marks a job completed before the object upload succeeds. If
it crashes after upload but before the database update, redelivery uses the
same object key and repairs the job state instead of creating another file.

## Rendering and storage

The worker renders a Jinja2 HTML certificate template with only the validated
job payload. WeasyPrint converts that HTML to PDF bytes. The worker uploads
bytes to the private MinIO bucket `documents` under
`certificates/{job_id}.pdf` with `application/pdf` content type.

The image installs WeasyPrint's required Pango runtime libraries. Templates
are application-owned and do not accept arbitrary user HTML or CSS.

## Deployment topology

The root Compose file gains:

- `rabbitmq`, with a healthcheck;
- `minio`, with a persistent volume and healthcheck;
- `documents-postgres`, with a dedicated persistent volume and healthcheck;
- `document-migrations`, which applies Alembic migrations then exits;
- `document-dispatcher`, restarted unless stopped and dependent on migrations
  and RabbitMQ;
- `document-api`, published on host port `8002`, restarted unless stopped;
- `document-worker`, restarted unless stopped and dependent on migrations,
  RabbitMQ, and MinIO.

MinIO bucket creation is an idempotent startup responsibility of a small
`minio-init` one-shot service before worker processing begins.

## Verification

- Unit-test the certificate renderer from a fixed payload and assert non-empty
  PDF bytes beginning with the PDF signature.
- Unit-test repository state changes, including repeat delivery of an already
  completed job.
- Unit-test dispatcher: it publishes each pending outbox row and marks it
  published only after Celery accepts the task.
- API-test creation (`202`), missing job (`404`), not-ready content (`409`),
  completed status, and PDF content response.
- Run migrations in a real Compose stack. Create a certificate through HTTP,
  poll to `completed`, download a valid PDF, and verify its object exists in
  the private MinIO bucket.

## Explicit non-goals

- Authentication, authorization, and document access policy.
- Cross-service student lookup or a student projection.
- Contracts, receipts, acts, document versioning, and regeneration UI.
- Public or presigned MinIO URLs.
- Retention policy, antivirus scanning, digital signatures, or cleanup jobs.
- A generic workflow engine.
